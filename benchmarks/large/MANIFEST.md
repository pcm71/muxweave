# benchmarks/large —— 真实规模用例（规模压力 + 混合组合逻辑 + 应用场景）

补齐 `unit/`（基础结构）与 `mixed/`（小规模混合）的缺口：**这是题目技术指标真正考核的规模**
（"节点规模 ≤1000 的电路，完整优化耗时 ≤60s，内存峰值 ≤2GB"）。

| 编号 | 文件 | 结构 | 目标规模 | 类别 |
|---|---|---|---|---|
| l01 | `l01_status_select.v` | 32 位 K=8 PMUX，高 16 位仅两个来源（字段重复） | ~百级 | 应用样本（状态字选择） |
| l02 | `l02_config_regfile.v` | 16×32 寄存器堆 + 16 路读回 PMUX | ~三百级 | 应用样本（寄存器读回） |
| l03 | `l03_field_mux_shared.v` | 4×24 位 K=8 PMUX，**共用同一 sel** + 算术/掩码 | ~三百级 | 混合组合逻辑 + 跨 PMUX 共享 |
| l04 | `l04_scale_bank.v` | generate 展开的并行阵列，`LANES` 控制规模 | LANES=4/8/12 ≈ 300/600/1000 | 规模压力 |

## 用法

```bash
# 单用例（B0 基线 / SCRIPT_ifarea 调优脚本）
python3 scripts/run_case.py --case benchmarks/large/l01_status_select.v --pipeline B0
python3 scripts/run_case.py --case benchmarks/large/l01_status_select.v --pipeline SCRIPT_ifarea

# 批量对比（含规模与效率指标）
bash scripts/wsl_large_eval.sh
```

## 纪律

1. **必须同时记录 CPU 时间与整进程峰值内存**（**内存口径见下方说明**）—— 规模用例正是用来验证 60s／2GB 门槛的。
2. 每个用例都要跑 **B0（官方基线）与最优变体**，按主办方口径算**逐用例平均缩减率**。
3. 用例规模以实测的 `逻辑单元` 为准登记到下表，不要按源码行数估算。
4. 若某用例在调优脚本下**变差**，必须记录 —— 选择策略必须能回退（方案第 8 节）。

> 内存口径：赛题阈值为峰值 ≤2GB。答疑早期（C26）称"内存是整个进程的峰值"，**最新 C54-2 明确"峰值工作内存，只看 yosys.exe"**。本项目历史记录多为整进程树峰值（**偏保守**，含 abc 子进程）。

## 规模调节

`l04_scale_bank.v` 的 `localparam LANES` 控制规模：4 ≈ 300、8 ≈ 600、12 ≈ 1000 节点级。
**注意**：早期版本每条通道只差 1 个 bit，8 条通道被优化折叠成 32 个单元（没起到规模压力作用）；
现版本每条通道用不同常数参与运算，LANES=12 实测 497 个单元。
