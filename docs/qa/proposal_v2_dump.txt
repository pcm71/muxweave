推荐结论与作品定位
推荐做一套“有实际优化算法的 Yosys 插件＋自动等价验证＋实验报告与可视化演示工具”。核心交付是能被 Tcl 调用、可批量处理未知测试用例的优化插件；界面负责解释优化效果和正确性证据。
主技术路线：识别 PMUX 的选择条件与数据位模式，进行跨位分组、选择条件共享和有限候选结构重构；在相同后端综合条件下比较资源，保留有收益且验证通过的结果。
最值得投入的差异化是：让多个数据位共同复用控制逻辑，并用映射后的真实资源反馈决定是否接受重构。 对单级 PMUX 做简单去重只是基础能力；只有相对默认流程和合理加强基线仍存在的增益，才构成作品的技术贡献。
本作品属于 EDA 软件算法类设计。主要工作集中于数字电路语义、C++ pass、验证和实验。官方指南已写明本赛题全部通过 eLinx 软件进行编译及仿真、无需硬件平台，且 eLinx 教育版不需要 license；评测侧统一使用 synth_intel 流程并把网表映射为 Cyclone IV 系列。提交前仍需与主办方复核 Yosys 插件与 eLinx 流程的最终衔接方式。
作品面向的使用者与使用流程
本作品首先服务于需要对含有多路选择逻辑的设计进行综合优化和对比实验的开发者。使用者提供 Verilog 文件、顶层模块、参数以及已经确认的基线配置，工具输出优化网表、验证状态和资源报告。评委则通过同一套入口复现结果，检查算法收益是否独立于人工操作。
典型使用过程分为六步：选择输入设计，确认基线与目标配置，运行结构分析，执行有限候选优化，检查形式验证状态，查看并导出报告。分析功能应能单独运行，方便在尚未启用重构时评估电路机会；正式优化功能必须把最终输出与对应验证记录绑定，避免用户误用未经验证的中间网表。
最小交付范围与扩展边界
第一版限制在同一模块中的组合逻辑重构，保持顶层接口、寄存器边界、复位语义和周期延迟。对时序电路，可以优化寄存器之间的组合部分，但不主动插入流水线、不改变状态编码，也不进行跨时钟域变换。这样可把主要精力用于资源优化，并降低验证难度。
分支优先级不明确、黑盒内部、带副作用或无法可靠建模的结构应明确报告跳过原因。跳过不是异常，必须区分“没有目标结构”“结构不在当前支持范围”“有目标但没有收益”和“工具运行失败”。这四种结果对用户采取下一步行动的含义不同。

报名 立项简介 规划版
本作品面向国产 FPGA 综合流程中多路选择器逻辑资源开销较大的问题，拟基于 Yosys 开发可通过 Tcl 调用的 PMUX 专用优化插件。系统围绕选择条件与数据位之间的重复结构，开展跨位分组、共享控制提取和有限候选结构重构，并通过统一后端映射评价优化收益。作品结合 EQY 形式等价验证、运行预算管理及失败回退机制，形成从 Verilog 输入、网表优化到验证报告的自动化流程。针对单级 PMUX、混合组合逻辑及具有应用背景的数据选择电路，计划实现题目要求的资源缩减和千节点规模性能指标，并提供结构对照、优化规则追踪、批量测试及反例展示，支撑结果复现与现场答辩。
完成实测后，用已验证的样本数、缩减率分布、时间及峰值内存替换“计划实现”；提交时不将目标数值写成实测成果。
一句话介绍：给 FPGA 的“多路选择开关”减少重复逻辑，同时提供可复查的正确性验证和资源对比。

评分：功能正确性 10%，优化效果 40%，算法效率 30%，设计文档 5%，现场答辩 15%。优化幅度达到 20% 以上，优化效果项可得满分。跨用例聚合方式已由主办方明确：按每个用例的平均算，主要看逻辑单元的优化效果；DFF 不作硬性要求，但不应多于优化前。
最重要的硬门槛：任一测试用例不等价，功能正确性得 0 分，其余项不予计分。 因此，正确性是必须通过的前提，不能按“只占 10%”分配很少精力。
效率细则：达标得基础分 20 分，任意指标超限 15% 以上不得分，若不超过所有指标的 5% 则得满分。主办方已确认“指标指的就是开销”：时间按 CPU 时间计，内存按整个进程的峰值计。“5% 条款”的确切含义以及 60 秒是否包含 EQY、基线计算与报告，仍待书面确认。因此本方案同时记录 CPU 时间与完整端到端墙钟时间、整进程树峰值内存，口径变化后无需重写测量系统。

建议主打 2 个算法贡献＋1 个工程贡献：
1. 选择集合驱动的跨位分组共享重构。
2. 面向映射收益和运行预算的有限候选选择。
3. 形式验证、回退和可追溯报告的一体化流程。
“创新点”在立项阶段是待验证的贡献假设。只有经过已有 pass 对比、消融和留出集检验后，才能在最终答辩中讲“优于基线”。没有开展文献与代码的完整查新，不写“首次”“国内首创”。
创新论证的可交付证据
拟创新点应先写成可被实验推翻的假设。例如：“当多个数据位包含重复的选择集合时，显式提取共享控制能够在固定映射后端上减少资源，且收益超过已有细粒度优化带来的收益。”这一假设同时给出了适用条件、比较对象和判断终点。
围绕每项假设保留四类材料：一个可以手工解释的小电路，一组不同参数或不同来源的电路，关闭该规则后的消融结果，以及收益不成立的反例。若只有一个精心构造样例受益，应把贡献描述为针对特定模式的优化，不扩大成通用显著提升。
专利或论文潜力可以在效果稳定后评估，但不把“申请数量”作为前期开发目标。应先检索相邻算法并核对实现差异，再讨论是否具备值得进一步保护或发表的内容。
必须理解的 PMUX 语义
Yosys 官方文档中，$pmux 的 A 是默认数据，B 是多路数据拼接，S 是多位选择信号。S 全零时输出 A；恰好一位为 1 时输出对应 B 切片；多位同时为 1 时输出未定义。不能仅凭名称将其当成任意 if/else 优先级网络。
第一版建议优先处理能由结构证明选择互斥的 PMUX，例如同一选择总线与不同完整常量比较形成的译码。对普通优先级 $mux 链，不自行改变选择优先级；对无法确认边界的结构，保留原实现或只应用已验证无条件成立的规则。
EQY 的官方语义是 safe-replacement equivalence：含未定义值时，这是有方向的安全替换，不一定等同于四值仿真逐位相同。因此应固定 gold=原始参考设计、gate=候选实现，并遵循官方评测的 X 与初态策略。
不能为了让验证通过，在参考设计中随意添加 one-hot 假设、把 X 全改成 0、交换 gold/gate 或删除不利输出。最终比较尽量从原始设计开始，防止错误预处理同时影响两侧而被掩盖。
局部证明如果依赖上游互斥关系，必须保留相应控制逻辑锥或已经证明的约束；不能把选择位切成完全独立输入后，假装上游条件仍然存在。

主算法 跨位分组与共享控制提取
为什么选择它
某些 PMUX 的各路完整数据字并不相同，但部分位或字段重复。整字去重可能找不到机会；按位发现重复后，可以让多个输出位共同复用“哪些分支会选择这类值”的控制表达式。
适合关注：寄存器读回字段、状态字选择、配置译码、常量字段插入、带公共字段的数据选择。完全独立的随机数据选择电路是重要负对照，不应期待同样收益。
直观例子
在已证明最多一个选择信号有效的情况下，若某一位上：
B0[j] = x，B1[j] = x，B2[j] = z，B3[j] = z
该位的数据选择项可分组为：
e01 = s0 OR s1
e23 = s2 OR s3
selected_j = (e01 AND x) OR (e23 AND z)
Y[j] = (none_selected AND A[j]) OR selected_j
若其他输出位也使用同样的分支分组，e01、e23 可以共用。这个例子仅解释代数机制，不是“已节省多少 LUT”的实验数据；已有 Yosys/ABC 优化也可能发现同样结果。
保留全零选择默认路径非常重要。不能只优化被选择的 B 项而漏掉 A。
可实现的步骤
1. 使用 Yosys 的规范化信号映射处理 wire alias，建立 PMUX 清单。
2. 提取每个 PMUX 的位宽 W、分支数 K、实际选择信号身份及各 B[i][j]。
3. 对每个数据位，按规范化后的信号或常量值聚类，获得分支集合。例如 {s0,s1} 对应同一个数据位信号。
4. 将选择集合规范化，构建共享表。缓存键必须包含真实 SigBit 身份、极性及作用域，不能只存局部下标 {0,1}。
5. 合并具有相同分组模式的相邻位片，保留更有利于后端处理的宽位结构。
6. 先用轻量成本估计过滤明显无收益或高扇出的共享。
7. 构造“保留原结构”和“分组共享重构”等候选，执行相同后端映射并比较。
8. 对将要保留的候选做正式等价检查；未通过则回退并记录原因。
初始实现只按结构相同判断数据位相等，不在每一对数据输入之间调用 SAT 证明函数等价。后者容易把范围扩展成昂贵的通用逻辑综合问题。
复杂度控制
特征提取的主要规模是所有 PMUX 的 W×K 之和，而不是“PMUX cell 数”本身。扫描和哈希分组可按输入位数近线性实现；避免全局任意两子图比较和指数级分区搜索。
节点数 ≤1000 不意味着任意位宽都小，所以测试必须同时记录节点数、位宽、分支数和总展开位数。首版可以为位片数量、共享表大小和候选数量设上限；超限保留原结构并记录，不崩溃、不静默改变功能。
与已有能力的边界
官方 opt_reduce 已包含重复 MUX 输入合并，-fine 还会执行细粒度优化；opt_merge 合并相同单元；opt_muxtree 删除不能激活的分支；opt_share 和 share 已涉及资源共享。因此，“发现重复就合并”不构成充分差异化。
必须检验本方案能否在这些 pass 和 ABC 之后仍获得收益。若没有，则将该规则降为预处理／辅助功能，不继续把它当作主创新。第 2 周需要做这项去留判断。

分组重构的算法草案
以下是结构化伪代码，用于明确实现职责，不是可以直接调用的现成函数。形式验证与最终成本判断应由正式驱动器完成。
input: normalized design and fixed evaluation configuration
reference = preserve_reference(design)
infos = collect_pmux_cells(design)
for info in infos:
    if not semantics_supported(info):
        record_skip(info)
        continue
    groups = group_equal_data_bits(info)
    patterns = merge_adjacent_compatible_bits(groups)
    proposals = extract_shared_select_sets(patterns)
    keep proposals within size and fanout budgets
candidates = build_bounded_design_candidates(reference, proposals)
for candidate in candidates before search_deadline:
    check_structure(candidate)
    evaluate_with_fixed_backend(candidate)
rank candidates using the confirmed resource metric
prove ranked candidates within the reserved proof budget
publish a verified candidate or the preserved reference
record adoption, fallback, timings, and resource measurements
采用此流程时要定义清晰的事务边界：候选构造可以失败，但原始参考设计必须始终可恢复。对一批规则的组合无法定位失败原因时，可以在调试模式下缩小变换集合或逐条开启规则；正式性能模式则避免为了定位错误不断重复昂贵证明。
分组粒度与控制开销
位级分析能发现细微重复，但完全位拆分可能增加控制逻辑并丢失后端可利用的宽位结构。因此建议先按位计算模式，再把相邻兼容位合并为位片输出。共享前需要统计一个控制集合被多少数据位使用，以及新增控制门是否被多处复用。
第一版先处理数据输入结构相同的情况；第二阶段再考虑同一模块中多个 PMUX 的共享。跨实例共享需要完整检查选择信号身份和作用域，且应控制扇出。跨层级模块共享会引入接口和层级保持问题，不列入十周版本的必做范围。

候选选择分两层：先依据 W、K、重复率、共享扇出和估计逻辑深度筛选；再对少量完整候选用固定后端得到真实单元数。首版每个设计最多 3～4 个全设计候选，不对每个 PMUX 独立生成所有组合。
成本评价先确保语义与工程约束成立，再最小化官方口径的单元数；相同单元数时偏好较小深度／扇出与较短耗时。启发式估计仅用于筛选，不作为正式资源结果。
所有候选映射、验证和基线准备的实际开销都要记账。若正式计时包含这些步骤，就不能把其中昂贵步骤移到“预处理”后从成绩里删除。
建议设置搜索截止点并预留验证、回退和输出时间。计时刚达到 60 秒才停止搜索已经太晚。具体预算在第 2 周基线测试后确定；不能在未测 EQY／后端开销时保证固定预算必然足够。
原结构回退能保障输出可用，但不自动保障面积指标达标。如果大部分用例都回退，作品可能正确但没有足够优化效果。
预算分配与终止条件
将总流程拆分为准备、分析、候选生成、后端评价、证明、输出六个阶段，分别记录墙钟时间。硬性总预算尚未明确时，同时记录完整端到端时间与每阶段时间，待主办方确认后无需重写测量系统。
搜索预算应由实测反推。设完整可用时间为总预算，先预留基线准备、最终证明、回退与输出的保守时间，再将剩余部分分配给候选搜索。若剩余预算不足以完成新的候选，就不再启动它。求解器和后端进程也要支持超时与结束后清理，不能只让驱动脚本停止等待。
停止条件可以包括候选数达到上限、共享表超过容量、预计扇出超过阈值、剩余时间不足以及连续候选无收益。阈值应保存为版本化配置，在留出集上保持固定，避免临时逐例调参。
接受候选的顺序
候选首先满足结构完整、语义前提和等价验证要求，再比较官方资源指标。相同资源数量时，可偏好深度较小、扇出较低、生成过程较短的候选。没有可靠时序模型时，只报告逻辑深度等代理指标，不称其为实际频率提升。
回退的参考应是同一次输入和同一公共流程产生的有效设计。报告中分别保留候选验证状态和最终输出状态：候选失败并回退之后，不能把“候选 PASS”写成绿色；应显示“候选未采用，最终保留参考设计”。

缺陷定位步骤
先固定触发问题的输入、工具版本和规则配置，再确认是语义错误、分区匹配问题还是工具错误。若存在反例，检查全零选择、切片方向、符号扩展、常量传播以及被共享信号的实际身份。随后生成尽量小的复现电路，修正规则，并将该用例加入永久回归集。
对时序输入，固定时钟、复位和初态条件；对组合电路，先在小例子上确认控制约束没有因分区而丢失。验证提速应优先采用合理分区与保留必要控制锥，不能通过删除不利输出或放宽输入约束实现。

资源缩减率：
r = Nbase - NoptNbase × 100%
N 必须是同一阶段的同一种计量，且基线与候选在同一 Cyclone IV 映射终点统计。主办方口径已明确：缩减率按每个用例分别计算再取平均，主要看逻辑单元的优化效果；DFF 不作硬性要求，但不应多于优化前。一个 32 位 $and 和一个 1 位门都记 1 个 RTLIL cell 时，raw cell 数不能直接说明实际面积。建议报告：
1. 官方口径全设计逻辑单元总数（DFF 单列）及分类型明细，作为主成绩。
2. PMUX 影响区域的单元变化，用于解释来源。
3. 映射到 Cyclone IV 系列网表后的 LUT、FF 等资源，以及 DFF 相对优化前的变化。
4. 逻辑深度；有可靠后端时报告关键路径／时序约束结果。
5. 优化流程 CPU 时间（分插件、综合映射、形式验证、报告四段）与完整端到端墙钟时间。
6. 整个相关进程树峰值内存，而非只测 Python 驱动进程。
同时呈现逐用例表与缩减率均值／中位数／最差值。评分采用“逐用例平均”口径，因此主成绩为平均(r_i)；加权口径 (ΣN_base−ΣN_opt)/ΣN_base 仅作参考并列展示，两种汇总不能混为一列。
小示例只能标“示意”：假如全电路原有 500 个单元、优化后 440 个，则缩减 12%；这不是本项目已测得的数据。
时间与内存测量办法
在固定机器上顺序执行性能样本，避免多个综合或证明任务争抢资源。每次记录 CPU、内存配置、操作系统、工具版本、线程设置和是否首次运行。主办方已确认耗时按 CPU 时间计、内存按整个进程的峰值计，因此每次运行必须同时保存 CPU 时间、墙钟时间与整进程峰值内存三项；可以重复三次并报告中位数与最大值，如果官方只执行一次，正式门槛仍按官方规则解释。
优先使用能够限制并统计整个任务进程组的操作系统机制，仅测 Python 父进程会漏掉 Yosys、ABC 和证明后端。在 Linux／WSL 下用 /usr/bin/time -v 或 cgroup 采集整进程峰值内存与 CPU 时间，基线与优化版本必须使用同一套采集方式。若临时使用周期采样，应同时说明采样间隔及可能漏掉短峰值的限制，不把它与严格峰值测量混同。
资源结果按每次运行实际导出的报告计算，不手动填入展示页面。导出前验证分母非零、前后阶段一致、目标库一致、结果状态有效。不同计数终点的记录应分别汇总，禁止混在同一缩减率列中。

消融实验与创新证据
需要的消融至少包括：B0、仅基础清理、仅跨位分组、跨位＋共享控制、加入候选选择、完整验证与回退流程。报告每种配置的面积（逻辑单元与 DFF 分列）、CPU 时间、整进程峰值内存和适用比例。
消融能回答：
面积收益由哪条规则产生？
控制共享是否只是将数据门减少，转化成更多控制门？
多候选选择增加多少收益，又增加多少时间？
某种规则在哪些电路无效，是否被自动跳过？
相比 opt_reduce -fine 等已有能力，剩余贡献是什么？
验证能力用受控错误测试展示，不把不做验证的产物作为正式可用版本。只有正确性已确认的变体才进入性能成绩比较。
可给每条被采用规则展示一张“优化证据卡”：输入特征、前提、结构变化、原始资源、最终资源、EQY 状态、日志位置。结构图上的节点变化与正式资源统计分开标识。
应用场景选择与收益上限
推荐主展示场景：具有重复字段的多源状态／寄存器读回选择模块。理由是选择结构自然、可参数化、容易画图，也容易加入非零默认值和混合组合逻辑。题目交付仍为通用优化插件，场景模块只是验证载体。
补充一个结构差异明显的应用场景，例如公共字段与有效载荷混合的数据字段选择。配置译码也可能被默认 ROM 推断很好地优化，因此用真实基线决定保留哪个场景，不预先承诺收益。
建议同时展示 1 个官方／通用测试用例和 1 个负对照。不要为了追求好看，做完整 CPU、视频系统、网络协议栈，导致 PMUX 工作成为附属。
提前估计全设计收益空间：若 PMUX 相关可优化逻辑占全设计资源比例 p，局部实际缩减比例为 q，其他资源近似不变，则全设计缩减约为 p×q。例如 p=0.30、q=0.40，则全设计约缩减 12%。这是立项估算，不是严格上界，因为共享可能影响其他逻辑。
若目标电路 PMUX 占比很低，单独把 PMUX 做得很好也未必达到全设计 20%。不能通过删除无关有效逻辑或改变分母来提高比例。

页面交互与结果追溯
展示页打开后默认呈现本次运行概要，用户点击某条优化记录可查看对应结构、前提和日志。面积数字旁同时显示计数阶段及基线编号，证明状态旁显示输入与候选标识。存在回退时，用文字说明原因，避免只用红绿颜色区分结果。
三张最值得制作的图是：前后结构图、逐用例资源缩减图、规模与时间关系图。前后结构图选择足够小的局部区域；性能图标清实际数据与时间范围；消融表说明每个配置开启了哪些规则。没有功耗或后端时序测量时，不加入推测性功耗百分比和最高频率数字。
演示故障预案
演示电脑提前固定环境并关闭自动更新引发的版本变化，现场入口使用本地文件。准备一个短时间可完成的小用例、一个完整历史运行目录和一段同版本录屏。实时证明超时，先说明当前状态，再切换到可核查历史记录；不修改页面数值掩盖失败。

延期时，先削减界面交互、附加场景和跨实例扩展，再减少候选数量。正确性验证、正式基线、混合逻辑覆盖和官方指标不能被取消。若时间不足以达成这些底线，需要调整参赛目标或选题，而不是把未达标包装成完成。

协作接口与交叉复核
A 与 B 共同确定规则前提和反例格式；B 与 C 共同确定结果状态、时间内存口径和报告字段；A 与 C 确定 Tcl 参数、错误码和输出目录。接口变更先更新一份共同维护的说明，再修改调用方，减少集成阶段的来回返工。
每周至少安排一次跨角色复核。A 解释本周一条优化为何成立，B 展示最难处理的失败用例，C 在干净目录中重新运行完整实验。三人应各自能够从命令行完成一条正式测试，不把答辩能力集中在负责人身上。
代码提交按规则或功能拆分，提交说明写明触发条件、变换和验证范围。实验结果应记录对应提交号，防止报告引用了无法再编译的旧版本。若指导教师参与，优先请其审查主规则的语义前提、基线公平性和第 2 周可行性结论。
工作量 设备和可行性
按每人每周 12～15 小时、3 人、10 周，预算约 360～450 人时。建议分配：规则与插件约 35%，验证与测试约 30%，工具链与实验自动化约 15%，展示与文档约 15%，机动约 5%。数字是排期预算，实际应根据第 2 周结果调整。
推荐开发电脑 16 GB 内存起步，有条件使用 32 GB；数 GB 至十几 GB 的工具和运行记录空间需提前预留。开发机总内存与比赛单次任务 2 GB 限额是不同概念，评测必须按约束控制实际进程资源。
项目不依赖 GPU、云服务或付费大模型。主要工具采用开源方案；本赛题通过 eLinx 完成编译及仿真，无需硬件平台，eLinx 教育版不需要 license，获取方式以主办方通知为准。预算优先保证可靠开发环境和备份，不先购买开发板。

资源投入与采购原则
预算以现有电脑、开源工具和主办方提供的软件为基础。优先保障磁盘空间、环境备份和可靠复现；临时租用算力只有在性能实验明确需要且评分环境允许时才考虑。目标板卡、付费工具与云服务均不作为当前路线的前置条件。
若后续需要安装 WSL、编译工具链或厂商软件，应单独按实际环境执行并核对版本。本文给出环境设计，不把“电脑已经装好工具”作为已成立事实。

核心算法没有收益时的诊断顺序
先确认比较终点和输入一致，再看 PMUX 在该电路中的资源占比。随后检查规则是否实际触发，以及新增控制门是否抵消数据通路减少。若规则触发且中间网表改善，但后端结果不变，可能是基线后端已经完成相同化简；此时增加相同样例数量不能解决问题。
可以调整插入点、控制共享范围和候选形态，但每次只改变一个主要因素并保留对照。若两周验证后仍没有独立于已有优化的效果，就将该规则降为分析或预处理功能，再对一个后备方向做小规模验证，不同时扩展成多个难以收尾的研究课题。

答辩表述示例
面对“是不是只是调用 Yosys 原有命令”，回答应从代码边界和实验对照展开：现有工具承担解析、通用综合与验证基础，团队实现的内容是具体的分组、共享、候选生成或选择机制；随后展示关闭自研规则后的变化。若没有增量结果，就不能用界面和自动化掩盖这一点。
面对“为什么不是所有用例都受益”，说明逻辑冗余分布不同，独立随机数据或已经充分优化的结构可能没有剩余空间；给出这些样本的真实结果和回退策略。清楚说明适用范围，比宣称对任意电路都有效更能体现技术理解。
面对“能否降低功耗”，应说明面积减少可能影响功耗，但还取决于切换活动、布线、频率和器件实现。没有可靠测量时，仅报告资源变化及后续测量计划，不把 LUT 缩减率直接当成功耗缩减率。
不建议作为主线的扩展
大模型自动修改 RTL：结果不稳定、额外依赖大，不能代替规则和形式证明。
强化学习／遗传算法全局搜索：如果没有现成基础，通常会放大时间预算与验证成本。
只调用已有 opt 命令再套 GUI：可以是工具集成练习，但不足以支撑本题的算法贡献。
全局最优布尔分解、跨时钟重定时、流水线插入：改变范围与验证难度；新增流水级还改变延迟。
先做漂亮界面、完整 SoC 或上板系统，再补优化：容易错配 40% 优化效果和 30% 效率的评分重心。
后续扩展的启动条件
跨模块共享、更多候选形态、目标器件定制成本模型和更强的形式策略可以作为后续路线，但应在基本指标稳定达标、独立测试通过、交付版本冻结后再启动。每项扩展先提出预期受益样本、新增验证负担和时间预算，再决定是否纳入比赛版本。
如果最终发现选择集合共享在特定寄存器读回或数据字段场景最有效，可以把下一阶段定位为这些场景的专用优化插件，积累独立项目验证。工程推广建立在明确适用条件和可重复结果上，不以扩大应用领域名称代替实际适配。
资料依据与使用边界
1. 用户提供《中科亿海微.pdf》，PDF 第 6～8 页（正文第 4～6 页）：题目要求、指标、评分、平台与软件获取说明。
2. Yosys 官方 Multiplexers 文档：https://yosyshq.readthedocs.io/projects/yosys/en/latest/cell/word_mux.html。已核对 A/B/S 语义、全零默认路径、多选未定义，以及不要过早破坏 mux 树的提醒。
3. Yosys 官方 Optimization passes：https://yosyshq.readthedocs.io/projects/yosys/en/latest/cmd/index_passes_opt.html。已核对 opt_reduce、opt_merge、opt_muxtree、opt_share、share、pmux2shiftx 等能力。
4. Yosys 官方 Command line reference：https://yosyshq.readthedocs.io/projects/yosys/en/latest/cmd_ref.html。已核对插件加载与 Tcl 脚本入口；具体构建和调用以冻结版本帮助为准。
5. EQY 官方 Equivalence and X-Propagation：https://yosyshq.readthedocs.io/projects/eqy/en/latest/xprop.html。已核对安全替换方向与 gold/gate 对 X 的不同解释。
6. 主办方问答记录《副本FPGA创新大赛问题汇总.xlsx》（2026.09.04、2026.09.11、2026.09.20 三批）：Yosys 版本、插件集成方式、synth_intel 后端、Cyclone IV 映射、缩减率聚合与效率口径的唯一依据。
7. 用户提供《亿灵思软件快速使用教程-20250328.pdf》：eLinx 建工程、编译、debug、ModelSim 联合仿真与时序约束的操作依据。
